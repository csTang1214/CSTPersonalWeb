ClinicCS

A full-stack conversational AI platform for a clinic: patients book, reschedule, and cancel appointments in natural language, and ask about hours, services, billing, prescriptions, and emergencies — with every informational answer grounded in real clinic documents by a hybrid retrieval pipeline. Recent work rebuilt that pipeline from dense-only vector search into a fused dense + lexical retriever with cross-encoder reranking, and added a full retrieval + LLM-judge evaluation harness to measure it.

Overview

One chat thread, two very different jobs

ClinicCS puts a single conversational agent in front of two distinct workloads. One is transactional — booking, rescheduling, and cancelling appointments — handled by a per-intent phase state machine that drives inline UI components (date picker, service picker, slot picker, confirmation) rendered directly in the chat thread. The other is informational — questions about clinic policy, hours, services, billing, insurance, prescriptions, and emergencies — answered by a retrieval-augmented generation pipeline over a curated knowledge base.

Everything the agent needs to answer comes from just two places: Postgres (structured appointment data plus the vector and lexical knowledge base) and Groq (generation). Embedding and reranking run in-process as local Transformers.js models — there is no external vector database and no third-party embedding API.

A fast 8B model classifies intent on every turn; only informational and transactional routing decisions that clear a confidence bar reach the 70B generation model. Session state lives in Redis with a 2-hour TTL and an in-memory fallback, so a single dev instance stays functional with no Redis at all.

🧭 Intent classification & routing

The classifier maps each message to one of 11 intents (booking, reschedule, cancellation, clinic info, services, payment/billing, insurance, prescription/referral, feedback/complaint, emergency, general inquiry) plus an OTHER catch-all. It sees the last two conversation turns as context so a follow-up like "and on Saturday?" inherits the topic instead of being re-guessed as a fresh booking. A sticky-intent rule keeps a multi-step booking in its transactional flow even when a mid-flow message would classify differently on its own.

📅 Transactional flow

Each transactional intent is a phase state machine — collecting → date_selection → service_selection → slot_selection → awaiting_confirmation → complete. Every phase emits an action that the SPA renders as an inline component, and the component's selection is POSTed back as the next message. Available services and slot times are read from the database (active doctors' specialties, RAG-parsed clinic hours with hard-coded fallbacks), availability is checked against existing rows before a slot picker is shown, and reschedule / cancel look the appointment up by id and patient_id so a patient can't touch someone else's booking.

🔎 Informational flow

Once the caller has decided a turn needs the knowledge base, the agent retrieves directly rather than through a forced LLM tool call — one fewer round trip and no dependence on the model choosing to call a tool. A single generation pass then runs: with context, the system prompt says to answer using only the clinic information provided and to name no phone / email / address that isn't in it; with no context, temperature drops to 0 and an explicit guard forbids inventing facts, hours, prices, or policies. Follow-ups re-retrieve — only bare acknowledgements ("thanks", "ok") skip RAG and reuse the cached context.

Retrieval Pipeline

Dense and lexical, fused in one SQL round trip

The corpus is three sources — 19 hand-authored clinic-policy markdown files, NIH patient Q&A (MedQuAD), and transcribed clinical notes (MTSamples) — chunked heading-aware to ~320 tokens and stored once in a single clinic_documents table.

🧱 Schema & indexes

One table carries the chunk text, a vector(384) embedding (bge-small-en-v1.5, cosine), and a generated tsvector over title + content. Three index types back it: an HNSW index (m=16, ef_construction=64) for dense ANN, a GIN index for lexical full-text, and btree indexes for section / source / doc filters. The migration aborts if pgvector is older than 0.5, since HNSW is required.

⚗️ Hybrid search + fusion

A query is embedded once (bge-small with an instruction prefix, Redis-cached), then a single SQL round trip runs both a dense branch (embedding <=> qv ordered, hnsw.ef_search=80) and a sparse branch (ts_rank_cd over websearch_to_tsquery). The two ranked lists are combined with Reciprocal Rank Fusion (Σ 1 / (60 + rank)) — no score normalization needed. A soft section pre-filter narrows to the intent-mapped section(s) but falls back to a global search and merges if the filtered result is weak.

🎯 Rerank & context build

The ~30 fused candidates are scored by a local cross-encoder (ms-marco-MiniLM-L-6-v2) as [query, passage] pairs and cut to the top 5; if reranking is disabled or errors, the pipeline degrades to RRF order. buildContext() then drops near-duplicate adjacent chunks and greedily fills a ~1200-token budget, prefixing each chunk with a provenance header, or emits the exact "No relevant information found in the clinic database." sentinel that the agent checks for to abstain.

🛡️ Grounding safeguards

Follow-ups always re-retrieve so an answer is never given from stale context; the classifier gets the last two turns so follow-ups aren't misrouted; a soft filter plus a minimum-RRF score gate routes genuinely unanswerable questions to the sentinel; an empty knowledge base forces temp 0 and a "do not invent" system message; the prompt forbids stating contact details not in context; and EMERGENCY is forced into the always-retrieve set so it's never handled from model memory alone.

Design Decisions

Trade-offs behind the system

Most of these are retrieval-quality-vs-latency or self-contained-vs-flexible calls, made with eval numbers rather than intuition where possible.

Hybrid retrieval + rerank vs. dense-only Retrieval quality
The decision

The original retriever was pure dense vector search. Fusing it with Postgres full-text via RRF and adding a cross-encoder rerank took Hit@5 from 0.74 to 1.00 and drove the unanswerable false-retrieval rate from 1.00 to 0.00 on the 33-question gold set — a lexical signal catches the exact-keyword policy questions that embeddings alone were missing.

The cost

The cross-encoder adds roughly 800 ms of p95 latency for only a small MRR gain over RRF alone on the current corpus, so it stays behind a RAG_RERANK flag to be re-evaluated as the knowledge base grows.

In-process models vs. external services Infrastructure
The decision

Embedding and reranking run as local Transformers.js models inside the Express process, and both dense and lexical search are just pgvector and Postgres full-text. No external vector DB, no embedding API, no per-query third-party cost — the whole retrieval stack is one Postgres instance plus the app.

The cost

First boot downloads ~120 MB of model weights, and the cross-encoder runs on CPU in the request path — acceptable for this scale, but not something that scales to heavy concurrent load without a dedicated inference service.

Retrieve directly vs. forced tool call Agent design
The decision

Once a heuristic decides a turn is informational, the agent calls the retriever itself rather than prompting the LLM to emit a tool call. It's model-agnostic and saves a full generation round trip on every informational turn.

The cost

The gate is a heuristic, not the model's own judgment — on a vague opening message the agent still occasionally volunteers semi-grounded specifics instead of asking a clarifying question first.

Abstain with a sentinel vs. always answer Safety
The decision

When retrieval comes back weak, the pipeline emits a fixed sentinel string and the agent says it doesn't have that information and points to the clinic — rather than letting a 70B model fill the gap. Agent-eval abstention correctness rose from 0.75 to 0.95 after the grounding fixes.

The cost

A strict score gate means the system will sometimes decline a question that the corpus actually could have answered if phrased differently — a deliberate lean toward "say less, correctly."

Evaluation

Measured, not assumed

Two eval layers run at different cadences — cheap deterministic retrieval metrics on every retriever change, and an LLM-as-judge generation pass before releases — plus an agent-level harness that drives the real agent and scores RAG as it actually uses it.

Retrieval metrics feed a suggested CI gate (fail on Recall@10 < 0.85, MRR@10 < 0.60, unanswerable false-retrieval > 0.15, or p95 > 1500 ms).

What's Next

Known limitations, honestly tracked

  • The intent → section pre-filter is marginal — a ~50–70% global-fallback rate on the current corpus suggests dropping the hand-written map for a learned router
  • Rerank cost is high for its gain at this corpus size — keep it behind a flag and re-benchmark as the knowledge base grows
  • Legacy pre-migration rows (old MiniLM embeddings) still live in the table — harmless but worth deleting once confident
  • The gold set is small (n ≈ 33) — expand it with held-out MedQuAD and real production failure cases
  • Vague-opener behaviour — make the agent ask a clarifying question instead of volunteering semi-grounded specifics
  • Migration and ingestion are still manual runbook steps, not automated on deploy
